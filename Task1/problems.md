### Задание 1. Анализ текущей интеграционной архитектуры

| Проблема                                                                          | Признаки                                                                                                                                                                                                                                                                   | Влияние на приложение                                                                                                                                                                                                                                 |
|:----------------------------------------------------------------------------------|:---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|:------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **1. Отсутствие идемпотентности и нестабильность платежного шлюза**               | **Jira:** INT-001 (деньги списываются, статус не фиксируется).<br>**SD:** SD-004 (зависание на 10 сек), SD-009 (двойное списание).<br>**Отзывы:** Марина (менеджер по развитию) — «Платежи падали, деньги списывались по два раза».                                        | Пользователь нажимает «Оплатить», приложение зависает, деньги списываются дважды. Из-за отсутствия идемпотентности статус платежа теряется. Это приведет к массовым возвратам, негативным отзывам в сторах и отказу пациентов от онлайн-оплаты.       |
| **2. Отсутствие идемпотентности и блокировки БД в сервисе «Расписание»**          | **Jira:** INT-005 (дубли записей при повторных POST), INT-009 (блокировки БД).<br>**SD:** SD-002 (ошибка Booking not found), SD-003 (дубль записи).<br>**Отзывы:** Дмитрий (техлид расписания) — «Нет идемпотентности, при двойном клике две записи».                      | При плохом интернете или двойном тапе пользователь создаст две записи на один слот. Из-за отсутствия репликации для чтения приложение будет долго грузить расписание в часы пик. Ошибки «Booking not found» сломают сценарий подтверждения записи.    |
| **3. Низкая отказоустойчивость и производительность legacy-системы 1С (Полисы)**  | **Jira:** INT-003 (ошибка 503 при >50 rps).<br>**SD:** SD-001 (зависание >30 сек), SD-008 (возврат null).<br>**Отзывы:** Алексей (разработчик интеграций) — «Контракт меняется без уведомлений (XML вместо JSON), rate limiting нет».                                      | Проверка полиса ДМС — критический шаг перед записью. При пиковой нагрузке (500+ пользователей) 1С упадет, и пользователи получат ложную ошибку «Полис недействителен». Нет механизма graceful degradation.                                            |
| **4. Ненадежная интеграция LIS (лаборатория) с CRM и мобильным приложением**      | **Jira:** INT-002 (FTP падает с ошибкой 425), INT-008 (дубли XML в CRM), INT-011 (неактуальные данные в CRM).<br>**SD:** SD-005 (задержка ночных анализов).<br>**Отзывы:** Анна (PO) — «Результаты задерживаются на часы», Алексей — «Коннектор на Perl без документации». | Главная боль пациентов — получение анализов. Задержка до 2 часов и сбои FTP-скриптов приведут к тому, что в приложении не будет актуальных результатов. Дубли анализов внесут путаницу в карточку пациента.                                           |
| **5. Переполнение очереди уведомлений (RabbitMQ) и отсутствие гарантии доставки** | **Jira:** INT-004 (нет документации по лимитам).<br>**SD:** SD-006 (очередь переполнена, пуши не приходят).<br>**Отзывы:** Елена (DevOps) — «Превысили лимит, очередь упала с ошибкой 404».                                                                                | В пиковые вечерние часы (целевая нагрузка MVP) пользователи не получат пуш-уведомления о подтверждении записи или готовности анализов. Это заставит их звонить в кол-центр, что противоречит цели MVP по снижению нагрузки.                           |
| **6. Уязвимости безопасности и подмена сессий**                                   | **Jira:** INT-006 (SQL-инъекция в веб-портале).<br>**SD:** SD-007 (врач видит чужого пациента, возможна подмена сессии).                                                                                                                                                   | Мобильное приложение будет работать с персональными и медицинскими данными. Подмена сессии или утечка данных через API приведут к огромным репутационным и юридическим рискам (нарушение ФЗ-152 о персональных данных).                               |
| **7. Отсутствие распределенного трейсинга (Observability)**                       | **Jira:** INT-007 (отсутствие distributed tracing, сложно найти корень сбоя).                                                                                                                                                                                              | При сбое в цепочке (Приложение -> API Gateway -> CRM -> LIS) невозможно быстро локализовать проблему. Время восстановления (MTTR) будет высоким, что критично при запуске мобильного приложения на 50 000 пользователей.                              |
| **8. Хрупкость контрактов API и отсутствие API Gateway**                          | **Jira:** INT-010 (необходимость API Gateway с rate limiting).<br>**Отзывы:** Алексей — «Вместо JSON стали возвращать XML и всё сломалось».                                                                                                                                | Прямые интеграции мобильного приложения с legacy-системами (1С, LIS) опасны. Изменение формата данных на стороне 1С или LIS мгновенно «уронит» мобильное приложение. Необходим слой абстракции (API Gateway) для валидации запросов и защиты бэкенда. |
