#### 1. Мобильное приложение -> API Gateway -> Микросервисы (Расписание, CRM)

* **Паттерн:** **API Gateway** + **Idempotency Key** (Ключ идемпотентности).
* **Стиль:** Микросервисная архитектура, Клиент-сервер.
* **Почему:** Прямой доступ мобильного приложения к «Расписанию» опасен (проблема INT-005, дубли записей). API Gateway
  становится единой точкой входа, которая:
    * Проверяет и ограничивает трафик (**Rate Limiting**), защищая бэкенд от пиковых нагрузок (цель — 500 RPS в MVP, 50
      000 в финале).
    * Реализует **идемпотентность** (если пользователь дважды нажал «Записаться», Gateway отсекает дубль по
      `Idempotency-Key`).
    * Обеспечивает безопасность (JWT-аутентификация, защита от SQL-инъекций INT-006) и маршрутизацию.

#### 2. Мобильное приложение -> API Gateway -> Адаптер 1С -> 1С (Полисы)

* **Паттерн:** **Adapter** (Адаптер) + **Circuit Breaker** (Предохранитель) + **Retry** (Повторные попытки).
* **Стиль:** Изоляция legacy-систем (Anti-Corruption Layer).
* **Почему:** 1С нестабильна (падает при >50 rps, тайм-ауты >30 сек, меняет контракты с JSON на XML). Прямая интеграция
  сломает приложение. Мы создаем «Адаптер 1С», который:
    * Транслирует современный REST/JSON от приложения в понятный 1С формат.
    * Использует **Circuit Breaker**: если 1С не отвечает 5 секунд, цепь размыкается, и мы мгновенно возвращаем
      пользователю ошибку (или используем fallback-логику), не подвешивая мобильное приложение.
    * Делает автоматические ретраи с экспоненциальной задержкой.

#### 3. Интеграция LIS -> CRM -> Мобильное приложение (Анализы)

* **Паттерн:** **Event-Driven Architecture** (Событийно-ориентированная архитектура) через **Message Broker** (
  Kafka/AMQP) + **Transactional Outbox**.
* **Стиль:** Асинхронный обмен сообщениями.
* **Почему:** Сейчас LIS передает данные в CRM через старый Perl-коннектор, который падает (INT-002, INT-008, INT-011).
  Использование брокера сообщений позволяет:
    * **Гарантировать доставку**: LIS (через адаптер) публикует событие `AnalysisReady`. Брокер хранит его, пока CRM не
      подтвердит получение.
    * **Избежать дублей**: Консьюмер (CRM) использует дедупликацию по ID сообщения.
  * **Сгладить пики**: Если CRM недоступна, сообщения копятся в очереди и обрабатываются позже, а пациент получает
      Push-уведомление, как только CRM обновилась.

#### 4. API Gateway -> Платёжный шлюз (Оплата)

* **Паттерн:** **Saga** (Распределенная сага) + **Transactional Outbox** + **Idempotency**.
* **Стиль:** Распределенные транзакции.
* **Почему:** Проблема двойных списаний (SD-009, INT-001). Внешний платежный шлюз работает синхронно, но деньги
  списываются, а статус теряется.
    * Мы используем `Idempotency-Key` при каждом запросе в платежный шлюз.
    * После успешного списания Gateway пишет событие `PaymentSuccess` в БД (Outbox) и отправляет его в брокер. Это
      гарантирует, что «Расписание» получит подтверждение оплаты, даже если сам API Gateway упадет сразу после списания
      денег.

#### 5. События -> Сервис уведомлений (Push/SMS)

* **Паттерн:** **Publish-Subscribe** (Издатель-Подписчик).
* **Стиль:** Асинхронная обработка.
* **Почему:** Сейчас RabbitMQ падает при переполнении (SD-006). Мы изолируем сервис уведомлений за брокером сообщений (с
  настройкой Dead Letter Queue для «потерянных» сообщений и кластеризацией). Уведомления не должны блокировать основной
  бизнес-процесс записи или оплаты.

#### 6. Все системы -> Observability Platform

* **Паттерн:** **Distributed Tracing** (Сквозная трассировка) + **Centralized Logging**.
* **Почему:** Решает INT-007. При целевом состоянии (50 000 RPS и <1 сек отклика) без сквозной трассировки (например,
  OpenTelemetry + Jaeger) невозможно будет найти узкое место при сбое.
