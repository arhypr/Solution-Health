### 1. Текстовое описание решения

**Цель решения:** Обеспечить гарантированную, быструю и отказоустойчивую доставку результатов анализов от лабораторной
системы (LIS) до мобильного приложения пациента, исключив дублирование записей и потерю данных.

**Выбранная архитектура:** Событийно-ориентированная архитектура (Event-Driven Architecture) на базе Apache Kafka (или
кластеризованного RabbitMQ с подтверждениями) с выделенным слоем интеграции (Адаптер LIS).

**Как это работает (Поток данных):**

1. **Готовность результата:** Анализатор передает данные в LIS. LIS фиксирует результат.
2. **Слой интеграции (LIS Adapter):** Специальный сервис-адаптер (заменяющий текущий Perl-коннектор) опрашивает LIS (
   через REST API) или получает вебхук. Адаптер нормализует данные (приводит XML/SOAP к современному JSON) и публикует
   событие `AnalysisCompleted` в брокер сообщений. *Если LIS временно недоступна, адаптер использует паттерн Retry с
   экспоненциальной задержкой.*
3. **Брокер сообщений:** Выступает буфером. Он гарантирует, что сообщение не потеряется, даже если CRM временно
   недоступна (хранит событие в топике/очереди).
4. **CRM (Консьюмер):** Читает сообщение из брокера. Реализует паттерн **Idempotent Consumer** (проверяет уникальный
   `analysis_id` в БД перед сохранением), что полностью исключает дублирование анализов (решает проблему INT-008).
5. **Уведомление:** После успешного сохранения в CRM, она публикует событие `ResultReadyForPatient` в брокер. Сервис
   уведомлений вычитывает его и отправляет Push-уведомление пациенту.
6. **Просмотр в приложении:** Пациент открывает приложение, которое через API Gateway запрашивает результат из CRM (
   синхронный REST-запрос для чтения).

**Почему это решает проблемы бизнеса:**

* **Гарантированная доставка:** Брокер сообщений хранит данные, пока CRM их не обработает (решает INT-011 — «застряло в
  очереди»).
* **Минимальная задержка:** Событие передается практически мгновенно (вместо текущих 2 часов задержки из-за FTP).
* **Отказоустойчивость:** Если CRM падает, сообщения копятся в топике, и когда CRM поднимается, она их все забирает.
* **Отсутствие дублей:** Дедупликация на уровне БД CRM и ключа сообщения.
* **Простота эксплуатации:** Мониторинг брокера сообщений позволяет сразу видеть, где «застрял» результат, а адаптер
  изолирует старые технологии LIS от новых систем.
