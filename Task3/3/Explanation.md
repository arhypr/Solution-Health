### 2. Комментарий к спецификации

#### Подход к версионированию API

В спецификации используется **версионирование через URL (`/api/v1/...`)**.

* **Почему выбран этот подход:** Это самый прозрачный и распространенный метод для мобильных приложений. Он позволяет
  легко маршрутизировать трафик на уровне API Gateway. Когда выйдет версия `/v2` с измененным контрактом (например,
  из-за отказа от 1С или изменения структуры данных), старые версии мобильных приложений, установленные у пациентов,
  продолжат работать с `/v1`, что обеспечивает обратную совместимость.
* **Альтернативы:** Версионирование через заголовки (`Accept: application/vnd.zdorovie.v1+json`) считается более "
  чистым" с точки зрения REST, но сложнее в отладке и кэшировании, а также требует дополнительной настройки на клиенте.

#### Подход к пагинации

В спецификации реализована **пагинация на основе смещения (Offset-based pagination)** с параметрами `limit` и `offset`.

* **Почему выбран этот подход:** Для MVP (цель — 500 RPS) и базового списка предстоящих записей этого достаточно.
  Пациент редко имеет сотни активных записей, поэтому смещение работает быстро. Это простой и понятный подход для
  клиентской разработки (легко реализовать бесконечный скролл или кнопку «Загрузить еще»).
* **Ограничения и план на будущее:** При переходе к финальной архитектуре (50 000 RPS) и увеличении объема данных
  offset-пагинация может стать узким горлышком из-за проблем с производительностью БД при больших смещениях (например,
  `offset=10000`). Кроме того, при добавлении новых записей данные могут "съезжать" между страницами. Поэтому в будущих
  версиях (v2) рекомендуется перейти на **курсорную пагинацию (Cursor-based)**, передавая в запросе `starting_after` (ID
  последней записи) вместо `offset`.

#### Безопасность и обработка ошибок

* **Аутентификация:** Используется стандарт **JWT (Bearer Token)**. Это позволяет API Gateway проверять подпись токена и
  извлекать `patient_id` без обращения к базе данных CRM на каждый запрос (что критично для нагрузки).
* **Ошибки:** Для 401 и 500 кодов возвращается унифицированная структура `ErrorResponse`. В ответ 500 добавлено поле
  `trace_id`, которое интегрируется с системой сквозной трассировки (Observability), чтобы разработчики могли быстро
  найти причину сбоя (решение проблемы INT-007).
